# ADR-006: 协作同步采用自研「中心广播 + 操作日志」，不使用 CRDT/OT

## Status: Accepted (2026-10-22)

## Background

用户输入的 OSS 清单给出结论：「唯一需要二开的功能是三维模型远程协作标注/实时交互」，并建议「基于现有 REST API + WebSocket 自建同步层」。

PRD OOS-03 已将「三维模型多人实时协作标注」列为明确不做，COL-01 列为 v2.0，理由是「需设计并发冲突合并策略，涉及操作语义定义（如两人同时修改同一结构的边界如何裁决），设计未完成前实现必然产生错误合并」。

作为架构师，本 ADR 的目的是：给出协作同步的**技术选型判断**，避免 v2.0 返工，同时为 v1.0 定义最小预留。

## Decision

**v2.0 采用自研「中心广播 + 操作日志」方案**，不使用 CRDT（Yjs）或 OT（ShareDB）。

**v1.0 只做数据模型预留**（约 0.3 人月）：`planning_plans.version` 乐观锁字段、`plan_commands` 操作日志表、WebSocket 网关位置（仅健康检查）。

## Rationale

核心论点是：**CRDT/OT 解决的是「字符/文本的收敛」，不是「医学标注语义的一致」。**

**1. 医学语义冲突无法由算法裁决**

两个医生同时调整同一条血管的边界，正确行为是**提示冲突、交人工裁决**——因为「哪条边界是对的」是医学判断，不是算法能决定的。

CRDT 在此场景会做什么？它会保证所有副本最终收敛到同一个结果，但这个结果是**静默合并**的结果。用户看到「同步成功」，实际得到的是一个临床上可能错误的模型。

这是医疗场景中最危险的失效模式——**沉默逻辑错误**：不报错、不崩溃、只是悄悄给出错误结果。这与 generated-code-failure-modes 中列为「最致命」的失效模式完全同类。

**2. 审计要求与 CRDT 内部结构冲突**

PRD AUD-01 要求每次涉及患者数据的操作可审计（记录操作人、时间、事件类型、患者标识、是否成功）。

CRDT 的文档状态是**二进制更新流**（Yjs 的 update 是合并后的二进制增量），无法直接映射为「谁在何时把某条血管的边界从 A 改成了 B」这样的审计条目。要从中还原业务语义，需要 CRDT 内部结构知识，审计不可读、不可解释——而审计必须能被质控科和司法举证读取。

操作日志模型天然满足：每条 `plan_commands` 记录 `command_type` + `before_value` + `after_value` + `user_id` + `created_at`，人可读、可查询、可导出。

**3. Yjs 的核心优势在阅片场景不成立**

| Yjs 优势 | 阅片场景是否成立 |
|---------|----------------|
| 离线优先 | 不成立——阅片是强在线场景，不存在离线编辑 |
| 富文本协同 | 不成立——标注不是富文本，是几何数据 |
| P2P 无中心协调 | 不成立——医疗数据必须受控，中心节点是合规要求 |
| 成熟的文档生态 | 不成立——3D labelmap 无成熟 CRDT 生态 |

Yjs 的四个核心优势在本场景全部不适用。而它的代价（tombstone 累积、内部状态不可读、3D 几何无成熟生态）全部成立。

**4. OT 同样不适配且更重**

OT 需要中心服务器定序，且转换矩阵随操作类型数量增长而复杂化。3D 标注的操作语义（新增/删除/布尔运算/平滑/边界微调）组合爆炸，且 OT 的正确实现难度随操作类型数增长，CKEditor 5 为树结构 OT 投入多年才完成即是例证。

**5. 操作日志 + 人工裁决是医疗场景的既有范式**

医疗系统的实际做法就是「冲突上抛人工」：PACS 修改冲突、EMR 并发编辑、HIS 医嘱冲突都是这个模式。这不是技术妥协，是场景决定的正确设计。

## Consequences

### 正面

- 避免 CRDT 在医学语义冲突下的静默错误合并
- 审计模型天然可读，满足 PRD AUD-01 与司法举证要求
- 无 tombstone 累积问题，无额外中间件
- 不引入 CRDT/OT 学习成本与调试复杂度
- 5 人以内协作规模下，中心广播延迟低（WebSocket，同机房 <50ms）

### 负面

- **不支持离线编辑**（这是明确的取舍，阅片场景不需要）
- 冲突时需要人工介入，不能自动合并
- 需自研操作日志与版本管理（约已计入 v1.0 的 0.3 人月，v2.0 另计）

### 实施要点（v2.0）

| 项 | 设计 |
|----|------|
| 通信 | WebSocket 中心广播，服务端推送操作事件 |
| 一致性 | 乐观锁（`version` 字段），冲突返回 HTTP 409 |
| 冲突处理 | 上抛人工裁决，不自动合并 |
| 权限 | 连接握手阶段携带 JWT 鉴权，不等到操作发生才校验（否则可绕前端直连 WebSocket） |
| 审计 | 每条操作经 `PlanCommandService` 产生可读日志 |

## Alternatives Considered

| 方案 | 否决原因 |
|------|---------|
| Yjs CRDT | 医学语义冲突静默合并（沉默逻辑错误）；内部状态不可审计；离线优先等核心优势在阅片场景不成立；3D labelmap 无成熟生态 |
| ShareDB OT | 中心定序仍无法裁决医学语义；转换矩阵复杂度随操作类型增长；调试成本高 |
| WebRTC P2P | 医疗数据必须受控于中心节点，不符合合规与审计要求 |
| 单纯 WebSocket 广播状态（最后写入者获胜） | 会静默覆盖他人修改，产生临床错误，且无法追溯被覆盖的内容 |
