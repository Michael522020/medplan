# ADR-009: MedPlan 仓库的公开策略与发布前脱敏门禁

## Status: Accepted (2026-10-27)

## Background

用户询问「能否上传到 GitHub 新建公开仓」。这是一个**合规敏感**的决策，
不能凭「代码是我写的所以随便发」来判断 —— 医疗信息系统一旦公开，
其架构、缺陷模式、防护机制的细节都会成为攻击者的参考图。

本轮我做了实际扫描（不是凭印象判断），结果如下。

### 扫描实测结果

| 检查项 | 结果 |
|--------|------|
| 真实患者标识（身份证/手机/住院号） | **0 命中** |
| 密钥/私钥/真实 API Key | **0 命中**（openapi.yaml 中的 `password: '********'` 是打码占位；JWT 示例是**编造的无效字符串** —— base64 解码失败） |
| 内网 IP（10.20.x.x / 172.x / 192.168.x） | 命中若干，但**全部为示例值** |
| 内网主机名（`medplan.internal` / `sso.hospital`） | 命中，示例值 |
| 本机真实网段比对 | 本机**无** 10.20.x.x 网段，且 ping 不可达 → 确认示例地址非真实环境泄露 |
| 真实姓名 | 均为掩码形式（`张*明`、`张××`） |
| 数据库口令 | 全部为 `medplan_ci_only` / `medplan_test_only` 这类**明显的测试值**，且无真实密钥 |
| git 仓库状态 | 尚未 `git init` |
| LICENSE 文件 | **不存在**，package.json 声明 `UNLICENSED` |

### 关键判断：技术上能公开，但**不建议以现状公开**

理由不是「怕泄露医院数据」（数据显示没有），而是三条更硬的理由：

**1. LICENSE 缺失 + 依赖许可兼容性未验证**
package.json 是 `UNLICENSED`，且无 LICENSE 文件。公开仓若无明确许可证，
法律上默认「保留所有权利」，别人不能用也不能改 —— 这与「开源」的初衷矛盾。
更关键的是**依赖许可兼容性尚未系统验证**：
- Cornerstone3D / OHIF：MIT（可闭源集成）
- dcm4chee-arc-light：MPL-2.0（文件级弱著佐权，可闭源）
- TotalSegmentator：主库 Apache-2.0，**但 46 个 task 中仅 31 个是 Apache-2.0**，
  `brain_aneurysm` 是 CC BY-NC 4.0（明确不给商业许可）
- React / NestJS / Fastify：MIT

组合起来是**可以**开源的，但必须先把「哪些文件受 NC 条款约束」标清楚。

**2. 医疗信息系统的「可用性即安全」属性**
这个系统一旦公开，其错误处理模式、越权判定逻辑、审计绕过路径都会成为
攻击者的参考。院内私有部署降低了这一风险；公开后无法收回。

**3. 等保三级测评语境下的「攻击面」考量**
PRD 中院方信息科的核心诉求原文是「最担心引入新系统增加攻击面」。
把防护逻辑全部公开，等于把攻击面说明书一并交出。

### 但也不必一刀切禁止

本项目**确实有公开价值**：
- 卫健委电子病历合规的落地实现（审计表物理不可改、hash chain、
  不可区分越权响应）是有价值的行业参考
- 「AI 合规边界做成编译期约束」的做法（`additionalProperties: false`
  + 13 条 `@ts-expect-error` 负向断言）值得被更多人采用

### 决策：单仓公开（2026-10-27 用户确认）

**用户决策：只建一个公开仓 `Michael522020/medplan`，采用 Apache-2.0。**

原方案是「私有交付仓 + 公开方法论仓」双仓。用户选择单仓公开，
理由是维护成本更低、对外呈现更完整。

因此本 ADR 的策略调整为：

| 项 | 决策 |
|---|---|
| 仓库 | `Michael522020/medplan`，**public** |
| 许可证 | **Apache-2.0**（与 dcm4chee 的 MPL-2.0、Cornerstone 的 MIT 兼容；含专利授权条款，对医疗软件有实际价值） |
| 交付给院方 | 同一仓库，但**部署配置由院方分支维护**，主分支不含院方定制内容 |
| 脱敏门禁 | `scripts/lint_publish.js` **15 条断言，公开前强制执行**，全绿才允许推送 |

### 单仓公开的额外要求（相比双仓更严）

单仓意味着**部署编排、完整契约、全部架构文档都在公开范围内**。
因此在原门禁基础上追加：

1. **README 顶部必须有「使用前必读」声明** —— 明确本项目不是医疗器械、
   不可直接用于临床诊断、合规状态为未认证。这是防止开源医疗项目被误用的第一道门。
2. **必须提供 `SECURITY.md`** —— 说明漏洞报告渠道，并**列出那些「看起来像漏洞但其实是设计决策」的点**
   （越权响应不可区分、审计表拒绝一切修改、AI 输出无诊断字段、签名用 SM3）。
   不写清楚，贡献者和用户会反复来问，甚至有人会去"修"这些设计。
3. **必须提供 `CONTRIBUTING.md`** —— 把硬约束（编译期合规边界、Token 单一源、
   单一图标库、许可合规约束、审计不可绕过）写成可执行的提交前检查清单。
4. **`.gitignore` 必须完整** —— 特别地：
   - **不能忽略 `package-lock.json`**。公开仓没有 lockfile 无法复现依赖，CI 也跑不稳。
   - 必须排除 `dist/`、`.env`、`*.pem`、`*.key`、日志、覆盖率产物。

### 公开前脱敏门禁（新增，必须实现）

新增 `scripts/lint_publish.js`，公开仓构建前强制执行：

1. 禁止出现真实内网网段（10.x / 172.16-31.x / 192.168.x）的**非示例值**
2. 禁止出现 `sso.*` / `*.hospital` / `*.internal` 等真实主机名模式
3. 禁止出现未打码的身份标识模式
4. 所有 `password` / `secret` / `token` 字面量必须来自白名单（测试占位值）
5. 依赖许可清单必须存在且无 NC 条款未标注项
6. 禁止出现 `.env` / `*.pem` / `*.key` / `*.p12` 等凭证文件

### 人工交叉审查（门禁管不到的类别）

门禁只能覆盖已知模式。公开前另行做了四项人工审查：

| 类别 | 结果 |
|------|------|
| 真实人名（中文姓名 + 职称） | **0 命中** |
| 具体医院/机构名 | **0 命中**（PRD 中「西安交大一附院」属竞品公开落地案例，公开信息） |
| 厂商/客户名 | 均为竞品调研引用的公开产品信息，正常 |
| 界面文案语言 | 零英文用户可见文案（英文仅出现在组件名/导入名/路由路径） |

## Consequences

### 正面
- 对外呈现完整，贡献者能看到从需求到代码的全链路
- 单仓维护成本低于双仓
- Apache-2.0 与全部主要依赖兼容，含专利授权条款
- 脱敏门禁 + 人工审查双重保障，公开内容可追溯（每条断言与审查项都有记录）

### 负面 / 注意
- **无法收回**：git 历史一旦推上去，公开仓的内容永久可挖。
  这是选择单仓公开时明确接受的代价 —— 换来的是完整的对外呈现。
- 主分支含部署编排与完整架构文档，**攻击面信息也一并公开**。
  这是本项目选择公开的既定风险，缓解手段是：只公开设计参考，
  不承诺可部署性；实际部署需院方自行完成全部合规工作。
- 交付院方时，主分支不含院方定制内容 —— 定制部分走院方分支。
