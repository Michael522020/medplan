# ADR-001: PACS 归档层选用 dcm4chee-arc-light 而非 Orthanc

## Status: Accepted (2026-10-22)

## Background

MedPlan 是院内浏览器阅片与手术规划前端，不接管影像归档（PRD OOS-04），但必须通过标准协议消费院内 PACS 的影像数据。架构上需要一个承担 DICOM 归档与 DICOMweb 服务能力的组件。

用户输入的 OSS 清单把 DCM4CHEE 定位为「企业级生产可用」、Orthanc 定位为「轻量级首选」，但未给出选型理由。在本项目的真实约束下（单院私有化、500 万幅影像、5 年留存、等保三级、DICOMweb 完整支持、HL7 对接国内 HIS），这两个定位会导出相反的结论，因此必须重新论证。

关键约束：
1. 数据不出院内网，私有化部署
2. 前端只能走 DICOMweb（WADO-RS / QIDO-RS / STOW-RS），浏览器无法讲 DIMSE
3. 需对接院内 HL7 v2 生态
4. 需长期维护，等保三级要求组件可审计

## Decision

采用 **dcm4chee-arc-light 5.35.2**（发布于 2026-10-15）作为 PACS 归档层。

不采用 Orthanc 1.12.9。

## Rationale

三条硬理由（非偏好排序）：

**1. 许可证是决定性因素**

Orthanc 采用 GPLv3（2025-08-11 版本 1.12.9 及其 DICOMweb 插件 1.21 均如此）。虽然纯内部使用不触发 GPL 的分发义务，但 MedPlan 是商业交付产品，影像数据在前后端与 PACS 间流转，商业交付形态难以界定，GPL 传染风险不可控。

dcm4chee-arc-light 采用 MPL-2.0，属文件级弱著佐权，允许在保留声明的前提下闭源集成，与商业交付形态天然兼容。

**2. HL7 v2 是国内医院刚需**

调研确认，国内 HIS/RIS 对接以 HL7 v2 MLLP 为主流。FHIR 在国内采用率地区差异极大（东部沿海三甲较高，中西部偏低），PRD 已排除 HIS 深度集成，本期不做 FHIR 服务端。dcm4chee 内置 HL7 v2 与监听器配置能力，Orthanc 需从零实现消息路由与确认机制。

**3. PostgreSQL 双写收益**

dcm4chee 元数据落 PostgreSQL，与业务库可用同一实例（不同 schema），审计与业务查询共用备份策略，减少一套运维体系。对 5 年留存要求是实质性简化。

补充理由：dcm4chee 原生提供完整 DICOMweb 三件套，Orthanc 需另装 dicomweb 插件，插件版本必须与主程序严格配套，升级时存在版本错配风险。

## Consequences

### 正面

- 无 GPL 传染风险，可商业闭源交付
- DICOMweb 与 HL7 v2 能力开箱可用，减少自研
- 容量上 PostgreSQL 支撑千万级索引，匹配 500 万幅目标
- Java 生态稳定，社区活跃，长期维护风险可控

### 负面

- 引入 Java 运行时，需 JVM 调优，运维复杂度高于 Orthanc 的单进程模型
- 与 PostgreSQL 实例若合并，需评估 PACS 元数据表对业务库性能的影响
- 团队需具备 Java 与 PostgreSQL 运维能力（或依赖运维团队）

### 中性

- 开发成本约 1.5 人月（对接与调优），高于 Orthanc 的配置成本，但低于 Orthanc + 自建 HL7/审计/队列的 2.5 人月

## Alternatives Considered

| 方案 | 否决原因 |
|------|---------|
| Orthanc 1.12.9 | GPLv3 商业风险不可控；HL7 与审计需大量自研 |
| 厂商 PACS（GE/西门子/飞利浦） | 闭源、信创适配差、厂商锁定、版本迭代不可控、对接成本高 |
| 自研 DICOM 归档 | 存储可靠性与 WORM 语义无法自证，等保三级下不可接受 |
