# ADR-005: 认证采用 Keycloak 26.8.1 + UKey 双因素；电子签名采用 SM2 + 采购密码机/TSA

## Status: Accepted (2026-10-22)

## Background

两个相关但必须分开的问题：

**问题一：登录认证。** PRD V1 要求双因素认证（口令 + 短信验证码）。GB/T 22239-2019 8.1.4.1 要求采用两种或两种以上组合鉴别技术，且其中一种至少使用密码技术。院内已有或将有统一身份系统。

**问题二：医师电子签名。** PRD COM-01 要求基于 CA 证书的可靠电子签名，签名绑定报告正文摘要值，使用权威可靠时间源。国卫办医发〔2017〕8 号第十条要求可靠的电子签名与手写签名或盖章具有同等法律效力，第十一条要求采用权威可靠时间源。WS/T 847—2024《医学电子文档数字签名技术标准》对医学电子文档数字签名提出具体技术要求。

## Decision

**认证**：Keycloak **26.8.1**（2026-10-13 发布）承载 OIDC 认证，双因素为**口令 + UKey 数字证书**（密码技术，满足等保要求）。

**电子签名**：不自研密码算法。采购持牌电子认证服务机构的医师个人数字证书（SM2，存于智能 USBKey）+ 采购密码机与签名验签服务器 + 采购权威 TSA 时间戳服务。应用层只做签名编排，密码运算全部委托密码机。

## Rationale

### 认证选 Keycloak 的理由

1. **OIDC 是标准化协议**：与院内既有身份系统解耦。院内很可能已有 LDAP、AD 或统一身份平台，Keycloak 可作为 OIDC Provider 对接，不强制替换既有体系。
2. **双因素由密码技术承载**：等保明确要求「其中一种至少使用密码技术」。短信验证码**不满足**密码技术要求，UKey 数字证书满足。这是对 PRD V1（口令 + 短信验证码）的必要修正——PRD 写的是验收示例，等保要求是硬约束，等保优先。
3. **避免自研认证的常见失效模式**：自研认证常见问题包括密码存储不安全、会话固定、会话不失效。Keycloak 是经过生产验证的成熟产品。

**版本说明（核实澄清）**：npm 上的 `keycloak` 包（1.2.0，2015 年发布）是一个无关的旧包，**不可与 Keycloak 服务器混用**。Keycloak 本体是 Java 应用，需从官方发行渠道部署。

### 签名不采用纯自研的理由

**1. 法律效力依赖持牌资质**

《电子签名法》要求可靠的电子签名，其实现依赖合法的电子认证服务。数字证书须由**持牌电子认证服务机构**签发（工信部许可）。这不是技术选择，是准入资格——自建 CA 无法获得同等法律效力。

调研确认的国内医院电子签名实现路径（多地医院采购公告口径一致）：
- 数字证书由持牌电子认证服务机构签发
- 核心运算支持 SM2/SM3/SM4 国密算法
- 配套密码设备（签名验签服务器、时间戳服务器）
- 时间源对接权威北斗授时
- 私有化部署院内，医疗文书数据不出院
- 系统按等保三级建设并配合密评

这些是**准入条件**，不是可选项。

**2. WS/T 847—2024 的具体要求**

该标准（国家卫健委发布）要求：
- 应先对签名人做基于数字证书的身份认证，确认其真实可信身份
- 应校验证书有效性与合法性（有效期、颁发者证书链、吊销列表），校验失败则不可签名
- 执行数字签名时，时间戳应**同时执行**，确保一一对应，有效证明数据的有效产生时间
- 签名日志应**独立于业务系统存储**，含数字签名流水号、原文唯一序列号、服务主体与对象标识、原文摘要值、摘要算法标识、证书序列号、签名数据等，且**日志本身可被数字签名**
- 应具备签名超时机制，超时后需重新身份认证

这些要求（尤其签名日志独立存储且自身可签名）说明自研的工作量与合规论证成本都很高，而采购方案直接满足。

**3. 密码机而非纯 UKey 的理由**

UKey 的 SM2 私钥运算在 UKey 内完成，物理安全；但**时间戳服务与审计留痕**仍需外部组件。密码机提供集中的签名/验签服务，便于：统一审计密码运算、统一时间源、多设备接入（移动签名场景 PRD 已排除，但架构预留）。私钥始终不出密码机。

**4. 密码算法绝不自研**

SM2/SM3/SM4 的正确实现需要密码工程能力与合规验证。自研密码算法在等保与密评下不可接受。

## Consequences

### 正面

- 认证侧满足等保 8.1.4.1 密码技术要求
- 签名具备法定效力，可用于病历归档、医保核查、质控检查、司法举证
- 密码运算委托密码机，私钥不落应用层，安全边界清晰
- 签名日志独立存储且自身可签名，满足 WS/T 847—2024
- Keycloak 通过 OIDC 与院内既有身份系统解耦，集成成本可控

### 负面

- **认证与签名是两套独立体系**（OIDC 会话 + CA 证书），需在前端分别承载，用户需插两次 UKey 体验割裂。缓解：签名环节是低频操作（每次报告 1 次），可接受
- 引入密码机、TSA、CA 三个外部依赖，交付链路长（风险 R8）
- Keycloak 是 Java 应用，增加一套中间件运维
- 证书年费为持续性支出

### 关键约束（写入实现规范）

- 签名必须先校验证书链与吊销列表，校验失败禁止签名
- 签名与时间戳必须同时执行，一一对应
- `signature_logs` 表独立于业务表，且需支持对日志自身的数字签名
- 前端签名弹窗 5 分钟无操作自动关闭，需重新 UKey 认证（WS/T 847 超时机制）
- 患者签名不在 MedPlan 范围（知情同意书属 HIS/EMR 职责）

## Alternatives Considered

| 方案 | 否决原因 |
|------|---------|
| 自建 CA 与自研签名 | 无法获得《电子签名法》要求的法定效力；不满足持牌机构准入 |
| 纯口令 + 短信验证码 | 不满足等保 8.1.4.1「至少一种使用密码技术」的硬要求 |
| 仅用 UKey 签名不用密码机 | 时间戳与密码运算审计需外部组件，架构上后续仍要补 |
| Keycloak 替代方案（自研 NestJS 认证模块） | 认证是典型「不该自研」的高风险模块；会话管理与密码安全易出错 |
| 第三方云签名服务 | 医疗数据不得出院（PRD OOS-07），云签名会将签名数据传出 |
