# ADR-008: 运行时 Node 版本锁定 22 LTS，忽略 codec-libjxl 的 EBADENGINE 警告

## Status: Accepted (2026-10-25)

## Background

`npm install` 会输出警告：

```
npm warn EBADENGINE Unsupported engine {
npm warn EBADENGINE   package: '@cornerstonejs/codec-libjxl@1.1.1',
npm warn EBADENGINE   required: { node: '>=24' },
npm warn EBADENGINE   current: { node: 'v22.22.2' }
npm warn EBADENGINE }
```

`@cornerstonejs/codec-libjxl` 是 `@cornerstonejs/dicom-image-loader@5.13.2` 的传递依赖
（`dicom-image-loader` 的 `decodeJPEGXL.js` 引用了它的 `/decodewasmjs` 入口）。

看到这条警告有两种可能的处置：
1. 升级运行时到 Node 24
2. 判定为误报，维持现状

若不查清就选 1，会带来连锁成本：Node 24 不在 LTS 窗口内，院内离线环境缺少
可用的安装源；而实际部署环境是**浏览器**（阅片在医生工作站浏览器里跑），
不是 Node。

## 调查过程

1. **查包内容**：`dist/` 下只有 `jpegxlwasm_decode.{js,wasm}` 与
   `jpegxlwasm_encode.{js,wasm}` —— 纯 WebAssembly，**无原生 `.node` 模块**
2. **查引用方式**：`dicom-image-loader/dist/esm/shared/decoders/decodeJPEGXL.js` 中
   `new URL('@cornerstonejs/codec-libjxl/decodewasm', import.meta.url)` —— 走浏览器
   URL 加载 wasm，**在浏览器主线程/Worker 中执行**
3. **实测加载**（本机 node 22.22.2）：

   ```
   import('@cornerstonejs/codec-libjxl/decodewasmjs')  -> 成功，导出 ['default']
   import('@cornerstonejs/codec-openjpeg/decodewasmjs') -> 成功
   ```

   薄层 CT 需要的 JPEG2000 解码器（`codec-openjpeg`，engines 无限制）
   与 JPEG XL 解码器**在 Node 22 下均能正常加载**。

## Decision

**运行时锁定 Node 22 LTS（>=22.12.0，以满足 Vite 8 要求），不因该警告升级到 Node 24。**

同时在根 `package.json` 的 `engines` 中明确：

```json
"engines": { "node": ">=22.12.0 <23" }
```

并加 CI 门禁断言：安装依赖时若出现 `EBADENGINE` 警告，**必须人工确认该包是否为浏览器端 WASM**，
不得据此盲目升级运行时。

## Consequences

### 正面
- 部署环境与院内离线镜像的 Node 版本要求保持在 LTS 窗口内
- 不引入 Node 24 的非 LTS 风险（Node 24 在本项目周期内可能变更 API）

### 负面 / 需要注意
- `npm install` 每次都会输出该 EBADENGINE 警告，**这是已知的、已调查过的、可以忽略的**。
  新人可能会误判为环境问题并尝试升级 —— 需在 README 中说明。
- 若将来项目引入 Node 端批量 DICOM 转码（不经浏览器直接处理影像），
  该场景下 libjxl 会被 Node 原生加载，此时才需要真正评估 Node 24。
  **当前 v1.0 范围不含该场景**（影像渲染全程在浏览器端）。

### 备选方案
- 升级 Node 24：否决。院内离线环境缺少可靠安装源，且非 LTS，
  收益为零（该包实际在浏览器运行）。
- 用 `overrides` 强制降级 codec-libjxl 到兼容版本：否决。
  会偏离上游 dicom-image-loader 的版本组合，增加解码行为不一致的风险。
