# ADR-007: 部署采用私有化 Kubernetes + 国密密码机（等保三级 + 密评）

## Status: Accepted (2026-10-22)

## Background

PRD 要求私有化部署、数据不出院院网、等保三级，并配合商用密码应用安全性评估（密评）。系统包含多个有状态组件：PACS（dcm4chee + PostgreSQL）、业务后端、GPU Worker、Redis、Keycloak、对象存储。

组件数量多、依赖关系复杂、密钥与证书需严格管控。

## Decision

采用**院内私有化 Kubernetes** 作为容器编排平台，配合**外购密码机与签名验签服务器**、**国密网关**、**权威 TSA 时间戳服务**。

不在 MVP 阶段引入服务网格（Service Mesh）。

## Rationale

**1. 组件数量决定必须用编排平台，不用 docker compose**

组件清单：PostgreSQL、Redis、dcm4chee、业务后端、GPU Worker、Keycloak、对象存储、前端静态资源，共 8+ 个有状态/无状态组件。需要：健康检查、自动重启、滚动升级、资源隔离（GPU Worker 需独占显存）。

用 docker compose 需自建这些能力，等保环境下不可接受。

**2. GPU 资源隔离是硬需求**

GPU Worker 需独占显存（≥12GB）与 GPU 调度。Kubernetes 的 `nvidia.com/gpu` 资源限定 + 节点亲和性可保证分割任务独占 GPU，避免多任务抢占显存导致 OOM（TotalSegmentator 显存 8–12GB，并发即溢出）。

这是不能用简单编排方案覆盖的真实约束。

**3. 等保三级要求密钥与凭据管控**

等保 8.1.4 要求鉴别信息保护、远程管理防窃听。落地措施：
- 密钥与凭据统一存 Kubernetes Secret（加密存储于 etcd）
- 禁止镜像内硬编码凭据
- 服务间 mTLS

**4. 密评（GB/T 39786-2021）要求四层密码防护**

| 层 | 措施 |
|----|------|
| 物理环境 | 机房物理门禁（院内机房） |
| 网络通信 | 国密网关（SM4 传输加密 + SM2 双向认证） |
| 设备计算 | 密码机（SM2/SM3/SM4 硬件运算）、堡垒机 |
| 应用数据 | 应用层调用密码机完成签名；SM4 加密敏感字段密钥 |

密码机在 K8s 中作为独立服务暴露（内部 gRPC/HTTPS），私钥不出密码机。

**5. 不引入 Service Mesh**

MVP 阶段服务数量有限（8 个组件），服务间通信用 mTLS + 内部网络分段即可。Service Mesh（Istio 等）会带来运维复杂度与性能开销，属于过度设计。后续若服务规模扩大再评估。

## Consequences

### 正面

- 健康检查、自动重启、滚动升级由平台提供，等保要求的基础运维能力达标
- GPU 独占调度，显存不被抢占
- 凭据集中管控，不落镜像
- 组件全容器化，支持离线环境（院内无外网）

### 负面

- K8s 本身有一定学习与运维门槛
- 院内需具备 K8s 运维能力（或采购运维服务）
- 密码机、TSA 等外购组件有采购与协调周期（风险 R8）

### 关键约束

- **离线交付**：全部镜像需在内网可用的私有 registry 中准备，不能依赖公网拉取
- **GPU 节点隔离**：GPU 节点打污点，GPU Worker 容忍污点，普通服务不调度到 GPU 节点
- **备份策略**：PostgreSQL 每日全量 + WAL 归档；audit_logs 独立备份（合规要求不可与业务数据同生共死）
- **时间同步**：全部节点对接 NTP；TSA 对接权威北斗授时（等保要求权威时间源）

### 最低资源规格（用于院方硬件基线核对）

| 节点角色 | 数量 | 规格 | 说明 |
|---------|------|------|------|
| GPU 节点 | 1（生产建议 2 做主备） | GPU 显存 ≥12GB（RTX 3090 / A10 级）；16 vCPU；64GB 内存；500GB SSD | TotalSegmentator 显存 8-12GB，须独占调度。显存不足则强制 `--fast` 并在报告标注降级 |
| 业务节点 | 2（K8s control-plane + 1 worker） | 8 vCPU / 32GB 内存 / 200GB SSD | 跑 PACS、后端、Keycloak、Redis、对象存储 |
| 存储 | 1 套 | NAS 或 SAN，起步 8TB，按 5 年影像增量预留 | 按三甲医院日均 CT 300 例 × 每例 1GB 估算 |
| 国密密码机 | 1 | SM2/SM3/SM4，QPS ≥2000 | 等保三级 + 密评（GB/T 39786-2021）四层防护硬要求 |

**结论**：院方若已有 RTX 3090 级 GPU 服务器，AI 层可直接复用；若只有 CPU，AI-01 的 10 分钟时限不成立，须换轻量模型或把 AI 分割降级为 P1。

## Alternatives Considered

| 方案 | 否决原因 |
|------|---------|
| docker compose | 无健康检查、自动重启、资源隔离；GPU 独占无法保证；不满足等保运维要求 |
| 物理机 + systemd | GPU 调度、滚动升级、凭据管控均需自建 |
| 虚拟机 + 自建脚本 | 介于 K8s 与 compose 之间，GPU 调度仍需自建 |
| 服务网格（Istio） | 8 个组件规模引入 Service Mesh 属过度设计，增加运维与性能开销 |
