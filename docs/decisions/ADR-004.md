# ADR-004: 数据库采用 PostgreSQL 18（业务主库 + PACS 元数据同实例）

## Status: Accepted (2026-10-22)

## Background

MedPlan 需要持久化：患者主索引（EMPI）、就诊、检查、序列、分割任务、分割结果、AI 确认记录、规划方案、报告、报告签名、审计日志、用户/角色/权限。

约束：
1. 等保三级要求审计记录防删除、防篡改、定期备份
2. 病历按国卫医发〔2013〕31 号需保存 15–30 年
3. 审计日志需支持多维检索（操作人、事件类型、患者标识、时间范围）
4. 数据不出院内网
5. 与 PACS（dcm4chee）共用基础设施，需考虑运维简化

## Decision

采用 **PostgreSQL 18**（2026-08-13 发布，EOL 2030-11-14）作为业务主库。

Redis **8.10.2**（2026-09-17）承担缓存、会话与分割任务队列（Redis Stream）。

PACS 元数据与业务库**共用同一 PostgreSQL 实例，以独立 schema 隔离**。

## Rationale

**1. 版本选择：18 的理由是 EOL 最长**

| 版本 | 发布 | EOL |
|------|------|-----|
| **18** | 2026-08-13 | **2030-11-14** |
| 17 | 2026-08-13 | 2029-11-08 |
| 16 | 2026-08-13 | 2028-11-09 |
| 15 | 2026-08-13 | 2027-11-11 |

本项目需长期维护（病历 15–30 年留存，代码维护周期 2 年以上），18 提供最长支持窗口。选 major 版本，minor 由部署方跟进安全补丁。

**2. PostgreSQL 而非 MySQL 的三个具体原因**

- **表级权限控制**：等保三级 8.1.4.2 要求「访问控制粒度达到主体用户级与客体数据库表级」。PostgreSQL 的 `GRANT/REVOKE` 可对 `audit_logs` 单独撤销 UPDATE/DELETE，实现审计表物理不可改；MySQL 的权限粒度在表级之上更弱。
- **JSONB 支持**：规划方案数据结构未定型（入路路径、角度、关键点），`jsonb` 可存方案数据同时建立 GIN 索引，避免过早固定 Schema（符合「避免过早优化」原则）。
- **扩展能力**：后续如需 pgvector 做相似检索，无需更换数据库。

**3. 审计防篡改的实现基础**

采用两条机制并用：
- 表级权限：`REVOKE UPDATE, DELETE ON audit_logs FROM app_user`，用数据库权限而非应用逻辑保证
- hash chain：`prev_hash` + `row_hash` 链式哈希，每次写入计算，可检测任意历史记录被篡改

**4. Redis 承担队列的理由**

分割任务是异步长任务（2–3 分钟），需队列支撑。相比引入 RabbitMQ（额外中间件 + 运维成本），Redis Stream 已在系统中（用于缓存与会话），零额外组件。

要求：至少一次投递，因此任务侧必须幂等（用任务 ID + 状态机保证）。

**5. PACS 元数据同实例**

dcm4chee 元数据已落 PostgreSQL（见 ADR-001）。同实例可让业务库与 PACS 共用备份策略、监控、故障恢复流程。对一个单院私有化系统，减少一套运维体系的价值大于理论上的隔离收益。

风险控制：需在部署文档明确说明，并在压测中验证 PACS 元数据表对业务库性能的影响。若影响显著，可拆分为独立实例（schema 隔离设计已保证拆分成本低）。

## Consequences

### 正面

- 审计不可篡改由数据库权限保证，不依赖应用代码正确性
- 长支持窗口匹配长期维护需求
- schema 隔离让业务表与 PACS 元表清晰分离，权限可独立管理
- 零额外中间件满足队列需求

### 负面

- PACS 元数据量增长可能影响业务库性能，需压测验证
- Redis Stream 的消费语义需自行实现（相比专业消息队列），需处理消息丢失与重复消费

### 关键约束（写入实现规范）

- 禁止在业务库与 PACS 元数据之间建跨 schema 外键（破坏可拆分性）
- `audit_logs` 专用写账号 `app_audit`，业务账号无 UPDATE/DELETE 权限
- 审计表建议按月 RANGE 分区，便于 5 年留存到期后 detach 归档
- 患者身份证号、手机号只存哈希（国密 SM3 或应用层 HMAC），不做明文落库

## Alternatives Considered

| 方案 | 否决原因 |
|------|---------|
| MySQL 8.x | 表级权限粒度不足以实现审计表物理防改；JSONB 能力弱于 jsonb |
| 独立 PostgreSQL 实例（业务 + PACS 分开） | 两套备份与监控，对单院系统运维负担过重；schema 隔离已能覆盖数据隔离需求 |
| MongoDB | 等保场景下关系约束与事务模型弱；审计表需要强 schema 与权限控制 |
| RabbitMQ 队列 | 引入额外中间件与运维成本；单链路异步任务用 Redis Stream 足够 |
| PostgreSQL + pgvector | 本期无向量检索需求，避免过度设计；需要时可直接加扩展 |
