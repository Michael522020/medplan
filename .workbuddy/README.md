# .workbuddy —— 开发过程记忆

> 这个目录记录本项目**开发过程中沉淀的实战经验**：踩过的坑、踩坑的根因、
> 以及尚未有定论的决策。
>
> **它不是产品代码，不参与构建，不被任何模块 import。**
> 但它是这个仓库里最有参考价值的部分之一 —— 医疗信息系统的合规落地，
> 真正难的地方不在写代码，而在那些「看起来没问题但会在特定条件下失效」的细节。

## memory/pitfalls.jsonl —— 踩坑库

每条记录一次真实踩坑，含稳定签名、错误家族、根因、修法、验证状态。

**为什么要公开**：这些坑大多是「合规约束 + 具体技术栈」交叉产生的，
不踩过一次很难提前想到。比如：

- `audit_logs` 按月分区，运行时新建的分区不继承 `ALTER DEFAULT PRIVILEGES` 的授权
  → 审计写入失败 → **审计事件丢失**（等保 8.1.4.3 不可接受）
- `GRANT` 写在 `REVOKE` 前面，授权被随后的撤销抹掉 → 审计专用账号实际写不进审计表
- plpgsql 函数体在**首次执行时**才解析函数名 → 扩展函数解析不到时，
  **迁移阶段完全不报错**，运行时才炸
- 行级触发器在空表上不执行 → 用空表验证触发器会得到「通过」的假象

**字段说明**

| 字段 | 含义 |
|------|------|
| `signature` | 稳定签名（剥离路径、行号、版本号），同一类错误才会累积到同一条 |
| `family` | 错误家族：dependency / runtime / type / build / test / database / security / tooling |
| `stack_fingerprint` | 技术栈指纹，用于**按依赖召回**而不是按需求文字匹配 |
| `root_cause` | 根因。写「在什么情形下、因为什么、会踩什么」 |
| `fix` | 修法 |
| `validated` | 是否已被机械证据验证（真实跑通 = true） |
| `recurring` | 修过还复发 = true，说明要换策略而不是再修一次 |

**怎么用**（在项目根目录）：

```bash
npm run recall:pitfalls          # 按当前技术栈召回相关坑
npm run recall:pitfalls --json   # JSON 格式，便于注入 AI 助手上下文
```

召回是**按技术栈指纹**匹配的 —— 需求文字一直在变（「分割」「阅片」天天说），
技术栈指纹才稳定。你装了 redis 客户端，就该召回 redis 相关的坑。

## memory/OPEN-DECISIONS.md —— 未决登记册

记录**定不下来、先放一放、等外部条件**的决策。

每条含：当前倾向、被什么阻塞、什么条件出现时可以关闭。
**只追加 + 就地关闭**，已关闭的项升格为 `docs/decisions/ADR-*.md`。

这个文件的价值在于：**它让「还没想清楚」变成一件被记录的事，而不是被忘掉的事**。
等保测评时，「哪些问题还没解决」是要能说清楚的。

## 为什么这个目录在仓库里而不是在开发者本地

- 踩坑经验**只有在有上下文时才值钱** —— 配上具体的表名、字段名、错误码才有用
- 私有仓库里没人会去看它，公开仓库里可能会帮到同样在做医疗系统的团队
- 它是「合规怎么落地」这个主题的**一手材料**，比二手文章真实

如果你觉得某个条目不该公开，删掉即可，不影响任何构建。
